# 评估 Agent：指标体系、评估方法与基准测试全解

> **这是什么:** Agent 系统怎么评估——**评估指标**（完成度/效率/鲁棒性/安全性）、**评估方法**（端到端 vs 分解、自动 vs 人工）、**基准测试套件**（GAIA / SWE-bench / AgentBench）。面试题 #17 的答案素材。
> **为什么重要:** "做得对不对"是所有 Agent 工程的第一性问题——LLM 输出不确定，没有评估就不知道系统是好是坏、改了是进步还是退步。面试官问这题，考的是**你有没有"度量意识"**。
> **本文定位:** 理论为主 + **每类指标都结合 BondSeek 生产指标落地**（引用覆盖率/检索命中/反思轮数/置信度——见可观测性案例）。读完你能回答"评估 Agent 到底评什么、怎么评"。
> **关联案例:** [可观测性](../../patterns/case-study-bondseek-observability.md)（指标的采集）| [防幻觉](../../patterns/case-study-bondseek-hallucination.md)（覆盖率/置信度的来源）

## 🎯 TL;DR 冲突摘要（先看这段）

> **这篇文档解决的核心矛盾：LLM 是"不确定的"，没法像普通软件那样"对就是对、错就是错"。** 传统后端点一个接口，返回 JSON 就成功；Agent 做一次任务，中间可能调了 20 次工具、绕了远路、最后答案还行但成本爆表——**"成功"到底怎么定义？**
> **破局方案是"多维度指标体系"：不要用一个分数冒充全部，而是分解成四个维度看——任务完成度（做没做成）、效率（花多钱多慢）、鲁棒性（换个说法还行不行）、安全性（有没有出格）。** 每个维度有对应指标：完成度看 **Success Rate / Pass@K**；效率看 **Cost / Latency**；鲁棒性看**扰动容忍度**；安全性看**违规率**。再加**方法**：既要**端到端整体打分**（用户真实体验），也要**分解评估**（单独看检索/推理/工具调用哪一环 Weak）；既要**自动评估器**（便宜可重复），也要**人工抽样**（抓自动评估抓不到的语义错误）；横向上对比**基准（GAIA / SWE-bench）**时还要看 **Effect Size（效应量）**——不是"涨了 3%"就说赢，要看增幅在统计上稳不稳。
> 读完全文你只需要带走一个模型：**评估 Agent = 多维度指标 + 端到端/分解双视角 + 自动/人工混合 + 有统计意识的对比。** 生产里要问的不是"Agent 答对了吗"，而是"**它答对的比例、花的钱、用的时间、遇到刁钻输入稳不稳、有没有越界——五个问题都能用数字回答**"。

## 1. 为什么评估 Agent 是难题（先理解问题）

| 传统软件 | Agent 系统 |
|---------|-----------|
| 输出确定（返回 JSON 就成功） | 输出不确定（答案有无数种写法） |
| 一次调用一个结果 | 一次任务一整个循环（几十次 LLM+工具调用） |
| 错误可复现 | 同一输入两次结果可能不同（温度/随机性） |
| 质量 = 功能正确性 | 质量 = 完成度 + 效率 + 鲁棒性 + 安全 综合 |

**核心难点**：**"成功"是多维的、模糊的、随机的**——所以需要指标体系而不是单分数。

---

## 2. 多维度评估模型（先看这张表）

> 对应 BondSeek 评估目录约定：每个评估设计按四维度分解，不搞"单一指标冒充综合评分"

| 评估维度 | 关键指标 | 评估方法 | 权重参考 | 回答什么问题 |
|---------|---------|---------|---------|------------|
| **任务完成度** | Success Rate / Pass@K | 端到端执行 | 40% | 做成没做成？ |
| **效率** | Cost / Latency / Token | 运行时日志 | 20% | 花多少、多慢？ |
| **鲁棒性** | 扰动容忍度 / 一致性 | 对抗性测试 | 20% | 换个说法还行吗？ |
| **安全性** | 违规率 / 拒绝正确率 | 红队测试 | 20% | 有没有越界？ |

**面试金句**：**单一指标是评估的大忌**——"回答正确率 90%"听起来很美，但可能它每答一次烧 5 块钱、要 2 分钟、换个问法就崩。**评估必须多维度，每个维度一个指标，综合加权，不是一个大分数。**

---

## 3. 第一维度：任务完成度（做没做成）

### 3.1 Success Rate（成功率）与 Pass@K

| 指标 | 定义 | 适用 |
|------|------|------|
| **Success Rate** | 一次尝试中任务成功的比例 | 任务"一次就要成"的场景 |
| **Pass@1** | 第一次尝试就成功的概率 | 追求"一次到位"（生产常用） |
| **Pass@K** | 尝试 K 次内至少成功一次 | 评估模型潜力（代码生成常用） |

**为什么要有 Pass@K**：LLM 有随机性——一次失败不代表能力不够。**Pass@3 比 Pass@1 更能反映"模型真实上限"**（自省范式：失败后重试 2 次看能不能救回来）。

### 3.2 端到端 vs 分解评估 ⭐

| 视角 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **端到端 (End-to-End)** | 给完整任务 → 看最终结果对不对 | 贴近真实用户体验 | 定位不了"哪一环 Weak" |
| **分解评估 (Decomposed)** | 拆开评：检索对不对 / 推理对不对 / 工具调得好不好 | 精准定位瓶颈环节 | 环节都对 ≠ 整体对 |

**典型分解维度（Agent 场景）**：
- **检索评估**：召回率（该找的都找着了吗）/ 精度（找到的是相关的吗）
- **推理评估**：中间 Thought 是否合理（难度高，常靠人工/大模型评审）
- **工具调用评估**：工具选对了吗 / 参数填对了吗 / 及时停止循环了吗

> **面试金句**：**端到端告诉你"好不好"，分解告诉你"哪一环不好"。** 生产优化必须两端都看——先端到端定位有大问题，再分解定位根因。

### 3.3 BondSeek 落地：端到端可观测指标

BondSeek 没有专门的评测集，但在生产埋了"端到端质量信号"：

| 指标 | 采集点 | 反映什么 |
|------|--------|---------|
| **引用覆盖率 (CitationCoverage)** | 幻觉检测阶段 | 答案带引用的句子比例——**越接近 100% 越好** |
| **置信度 (Confidence)** | 幻觉检测输出 | 答案可信度 0~1——低于阈值触发重做 |
| **检索命中** | RAG 埋点 | 检到多少 chunk/实体/关系——**0 命中 = 这次必答不好** |

## 4. 第二维度：效率（花多少钱、多慢）

LLM 应用效率 = 成本 + 延迟，两者密切相关（慢通常也贵）。

| 指标 | 定义 | 优化方向 |
|------|------|---------|
| **Cost（成本）** | 一次任务消耗的 token/美元 | 降 token：压缩上下文、精简工具结果、一次调用干多事 |
| **Latency（延迟）** | 一次任务总耗时 | 降延迟：并行工具调用、流式输出、减少循环轮数 |
| **Token 消耗** | 输入+输出 token 总量 | Token 审计：每次 Agent 决策(循环轮数)都是钱 |

**BondSeek 落地**：工具调用树的**节点数 = LLM 调用次数**（可换算 token 成本）；反思轮数（`ReflectionRounds`）是"质量 vs 成本"的跷跷板——**质量不满意重做一轮，成本+一轮**。

> **面试金句**：效率指标是 Agent 的"性价比账本"——**每个循环轮数、每次反思重做、每段塞进上下文的结果，都直接等于钱和时间。** 效率评估不是数字游戏，是"这个 Agent 值不值"的商业问题。

## 5. 第三维度：鲁棒性（换个说法还行吗）

Agent 的现实输入远比测试集刁钻：

| 鲁棒性测试 | 做法 | 常见翻车点 |
|-----------|------|-----------|
| **改写输入** | 同意思不同问法 | 提示词自定义 → 模型理解跑偏 |
| **加噪声** | 输入带错别字/口语/打断 | 解析失败、理解错误 |
| **对抗扰动** | 故意刁钻问题/诱导 | 被误导、回答偏离主题 |
| **长对话漂移** | 连续多轮后质量下降 | 上下文污染、忘了最初意图 |

> **面试金句**：鲁棒性评估的经典陷阱是"**测试集过拟合**"——Agent 在标准测试集上 95 分，用户一换问法就崩。**鲁棒性 = 换着花样攻击你，看你还稳不稳。**

---

## 6. 第四维度：安全性（越界就完蛋）

| 安全指标 | 定义 | 场景 |
|---------|------|------|
| **违规率** | 回答中违反政策/出格的比例 | 金融合规（不能给"保证收益"建议） |
| **拒绝正确率** | 该拒绝时正确拒绝的比例 | 越狱/危险操作 |
| **敏感信息泄露** | 是否吐出不该说的 | 用户隐私 / 公司数据 |

**BondSeek 落地**：金融场景安全是红线——审计日志脱敏（不记录密码 Token）、记忆丢弃留痕（证明"为什么没记住"）、引用强制带出处（防编造）。**评估 Agent 时安全维度不能只靠自动指标，要配红队人工测试。**

## 7. 评估方法：自动 vs 人工（怎么评）

| 方法 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| **自动评估器（LLM-as-Judge）** | 便宜、可重复、海量 | 大模型评审本身可能偏 | 批量回归（每次改完跑一遍） |
| **规则/单元测试** | 绝对客观 | 只能测"结构化"部分 | 工具调用参数/检索命中 |
| **人工评估** | 最准（语义细节） | 贵、慢、不一致 | 抽样抽查 / 上线前验收 |

**生产最佳实践**（三合一）：
```
每次发版 → 自动回归（LLM-as-Judge + 规则检查）→ 覆盖 80% 用例
每周 → 人工抽样 50 条真实对话 → 抓语义错误
线上 → 可观测性埋点（覆盖率/置信度/用户反馈）→ 持续看真实表现
```

> **面试金句**：**自动评估用来"防退步"（回归），人工评估用来"抓语义"，线上指标用来"看真实"。** 三层都有才算评估闭环。

## 8. 基准测试套件（横向对比用什么）

> 业界标准基准——面试能报出名字和测什么，说明你知道"Agent 能力怎么横向比"。

| 基准 | 全称/性质 | 测什么 | 典型难度 |
|------|-----------|--------|---------|
| **GAIA** | 通用 AI 助手基准 | 真实世界多步任务（查资料/推理/组合） | 极难（人类 >80%，模型 ~40%） |
| **SWE-bench** | 软件工程基准 | 修真实 GitHub issue（读代码+改代码） | 难（最佳模型 ~1/3） |
| **AgentBench** | 多环境综合 | 8 个环境（游戏/网页/代码/Database）的 Agent 能力 | 综合 |

**基准对比的注意点（数据污染）**：**基准题目可能已泄露进模型训练数据**——模型"背会"了答案≠能力。所以对比时看 **Effect Size（效应量）**，不只看裸分数。

### Effect Size（效应量）——对比不是"涨了就说赢"

| Effect Size | 标准 |
|------------|------|
| d < 0.2 | 无差异 |
| 0.2 ≤ d < 0.5 | 小 |
| 0.5 ≤ d < 0.8 | 中 |
| d ≥ 0.8 | 大 |

```markdown
| 系统 | GAIA (Pass@1) | Effect Size vs Baseline |
|------|---------------|------------------------|
| Baseline | 22.5% | — |
| System A | 31.8% | d=0.73 (Medium) |
| System B | 42.5% | d=1.48 (Large) |
```

**面试点**：**"我们比基线涨了 9 个点"不如"效应量大"**——小样本上涨幅可能纯属随机波动，Effect Size 告诉你"这个涨幅在统计上有多可信"。

## 9. 面试回答框架（30 秒版）

### 送分版（只说维度+指标）

> "评估 Agent 要**多维度**而不是单一分数。主要分四个维度：**任务完成度**——看 Success Rate 和 Pass@K，既看端到端成功，也拆开看检索/推理/工具调用哪一环 Weak；**效率**——Cost / Latency / Token 消耗，Agent 每个循环轮数都是钱；**鲁棒性**——改写输入、加噪声、长对话漂移还稳不稳；**安全性**——违规率、拒绝正确率、敏感信息泄露。方法上**自动评估（LLM-as-Judge）防退步、人工评估抓语义、线上指标看真实**，横向对比用 GAIA / SWE-bench 等基准，且要看 Effect Size 而不是裸分数。"

### 加分版（+ 决策导向 + 结合项目）⭐

> "我补充三点体会。**第一，评估要'为决策服务'**——指标不是越多越好，每个指标都要能回答一个决策问题：'要不要上线/要不要改 /哪个环节先优化'。**第二，分解评估是优化利器**——我们 BondSeek 里端到端看引用覆盖率和置信度（低于阈值触发重新生成），分解看检索命中数（命中 0 = 这轮必答不好）、工具调用树的耗时和轮数（哪里绕了远路）。**第三，评估节奏要闭环**——发版自动回归防退步，每周人工抽样抓自动评估抓不到的语义错误，线上可观测埋点持续看真实表现。Agent 评估最难的不是定指标，而是**让指标真正驱动优化决策**——否则只是数字装饰。"

## 反模式（本主题避免）

- **单一指标冒充综合评分**——必须多维度分解（完成度/效率/鲁棒性/安全）
- **只看端到端不打分解**——定位不了"哪一环 Weak"
- **自动评估一统天下**——大模型评审有偏见，人工抽样不可省
- **裸分数对比不讲效应量**——"涨 3%"可能纯属随机波动
- **忽视数据污染**——基准题可能已泄露进训练数据（背答案≠能力）
- **评估不反馈决策**——指标算完不用，等于没评
