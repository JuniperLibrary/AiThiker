# 认知架构范式对比：ReAct / Plan-and-Execute / Reflection

> **这是什么:** 认知架构（Cognitive Architecture）三大范式对比——**ReAct**（边想边做）、**Plan-and-Execute**（先计划后执行）、**Reflection**（先做后审）。它们回答同一个问题："Agent 的'思考'和'行动'如何组织？"
> **为什么重要:** 面试官问"你用的 Agent 是哪种范式"——不是考名词，是考你**知不知道自己在用什么编排方式、为什么选它**。三种范式不是互斥的，**生产系统通常是组合拳**。
> **本文定位:** 面试题 #14 的答案素材（第三梯队首题）。配合 BondSeek 案例看"生产里范式怎么落地"。
> **关联案例:** [多 Agent 编排](../../patterns/case-study-bondseek-multi-agent.md) | [防幻觉体系](../../patterns/case-study-bondseek-hallucination.md) | [RAG 检索](../../patterns/case-study-bondseek-rag.md) | 总纲 [`from-zero-to-agent.md`](./from-zero-to-agent.md)

## 📌 名词速查表（先看这里）

| 英文 | 读作/理解成 | 一句话解释 |
|------|------------|-----------|
| **Cognitive Architecture** | "认知架构（专有名词）" | Agent 的"大脑组织方式"——思考/行动/记忆怎么编排 |
| **ReAct** | "边想边做（专有名词）" | 推理（Reason）+ 行动（Act）交替循环，每一步想完就动手 |
| **Plan-and-Execute** | "先计划后执行（专有名词）" | 先让模型产出完整计划，再按清单逐步执行 |
| **Reflection** | "反思（专有名词）" | 生成答案后自我检查、发现问题、重做 |
| **Loop** | "循环" | Agent 反复执行"想→做→看"直到任务完成 |
| **Tool** | "工具" | 模型可调用的外部能力（查库/执行代码/调 API） |
| **Thought** | "思考" | 模型解释自己为什么这么做的一段推理 |
| **Sub-Goal** | "子目标" | 大计划拆出来的小步骤 |
| **Self-Critique** | "自我批评" | 模型评价自己输出好坏的能力 |

## 🎯 TL;DR 冲突摘要（先看这段）

> **这篇文档解决的核心矛盾：模型是"一步到位的嘴炮"——你让它直接给答案，它要么答得浅（没查资料）、要么答得错（不会纠错）、要么一步走死（遇到岔路就懵）。** 三大范式就是三种"组织思考和行动"的套路：
> **ReAct = 边想边做**（走一步看一步，适合探索型任务）；**Plan-and-Execute = 先想后做**（全局规划再执行，适合确定性任务）；**Reflection = 做完再审**（自我检查重做，适合质量敏感任务）。
> 它们不是选择题——**生产系统永远是组合拳**：ReAct 打底、叠加 Plan 约束、穿插 Reflection 质检。读完全文你只需要带走一个画面：**把"想"和"做"的不同排列方式看成三种乐器——ReAct 是即兴爵士（高频决策）、Plan-and-Execute 是交响乐谱（长链规划）、Reflection 是录音回放（质检重录），背后是同一个乐队指挥。**

## 1. 三大范式全景对比（先看这张表）

| 维度 | **ReAct**（边想边做） | **Plan-and-Execute**（先计划后执行） | **Reflection**（先做后审） |
|------|----------------------|-----------------------------------|---------------------------|
| 核心思路 | 想一步 → 做一步 → 看结果 → 再想 | 先产出完整计划 → 按清单逐条执行 | 生成答案 → 自检 → 不合格重做 |
| 决策频率 | 每步都决策（高频） | 计划时决策一次（低频） | 完成后决策一次（收尾） |
| 适合任务 | 探索型、信息不全、需要边走边看 | 确定性、步骤清晰、长链路 | 质量敏感、错误代价高 |
| 最大优点 | 灵活，能应对意外 | 可预测、可跟踪进度 | 提升质量、减少幻觉 |
| 最大缺点 | 容易跑偏、token 消耗大 | 计划跟不上变化、死板 | 额外时间和 token、可能过度自我否定 |
| 形象类比 | 即兴爵士 | 交响乐谱 | 录音后回放质检 |
| 框架对应 | LangGraph `REACT` | LangGraph `PLAN_EXECUTE` / `PLAN` | Self-Refine / CRITIC |

**一句话记忆**：
- **ReAct = 想→做→想→做**（思考穿插在动作里）
- **Plan-and-Execute = 想完（计划）→ 做→做→做**（思考集中在前段）
- **Reflection = 做→审→（重做）→审**（思考集中在后段）

## 2. ReAct：边想边做（最经典的范式）

### 2.1 循环长什么样

```
输入问题
  ↓
Thought: 用户问债券对比，我需要先查两只债券的基本面
  ↓
Action: search_bonds("XX 债券")
  ↓
Observation: 返回 XX 评级 AA+、票面 3.2%...
  ↓
Thought: 还需对比 YY 的违约风险，再查一下
  ↓
Action: search_bonds("YY 债券")
  ↓
Observation: 返回 YY 评级 AA-、票面 3.8%...
  ↓
Thought: 数据齐了，可以给出对比结论
  ↓
Action: Final Answer
```

**关键点**：模型**每个循环都输出三段**——`Thought`（我为什么这么想）、`Action`（我要做什么）、`Observation`（做完看到了什么）。这就是"Reason + Act"（推理 + 行动）名字的由来。

### 2.2 为什么它最流行

| 优点 | 说明 |
|------|------|
| **拒绝一路错到底** | 每步看结果再决定下一步，错的路径能及时掉头 |
| **工具利用率高** | 复杂任务必然要查多轮资料，ReAct 天然支持 |
| **可解释性** | Thought 序列就是答题过程，方便审计和前端展示 |

### 2.3 它的坑

| 坑 | 说明 | 缓解 |
|----|------|------|
| **无限循环** | 模型可能反复调同一个工具不收敛 | 轮数上限（max_iterations）+ 相同动作熔断 |
| **token 爆炸** | 每轮都带全部历史，几十轮后窗口爆 | 上下文压缩/剪枝（见记忆案例） |
| **被观察带偏** | Observation 太长太大，模型抓不住重点 | 工具结果裁剪/摘要后再喂给模型 |

### 2.4 生产中的落地形态

**ReAct 是"循环兜底"**——落到 BondSeek，就是多 Agent 案例里的**统一执行引擎**：循环只写一遍，通过不同的系统提示词 + 工具集 + 轮数上限构建不同角色。**你不需要为每个 Agent 重新写循环——ReAct 循环本身是共享的，换的是"提示词 + 工具"这套插件。**

## 3. Plan-and-Execute：先计划后执行

### 3.1 和 ReAct 的核心区别

```
ReAct 模式：
  Query → [想→做→看] → [想→做→看] → ... → Answer
                 ↑ 每次都不知道下一步去哪，边走边定

Plan-and-Execute 模式：
  Query → 计划（一次性想清楚几步）→ 执行步1 → 执行步2 → ... → Answer
                 ↑ 计划先定好，执行阶段不再动脑规划
```

**最大优势**：**可预测性**。管理者（或用户）能先看到完整计划——"它打算先查评级、再算收益、最后对比回撤"，心里有底；每步执行完打勾，进度可视化。

**典型适用**：用户给了一个明确的多步任务（"分析这 5 只债券，分别给评级、票息、久期、最后横向对比"）——步骤确定，最好先列计划。

### 3.2 三个工程要点

| 要点 | 说明 |
|------|------|
| **计划质量决定一切** | 计划错了后面全错——计划阶段要用强模型/加验证 |
| **计划要可执行** | 每步必须是"工具能完成的最小动作"，不能抽象成"分析债券"这种大词 |
| **需要重规划机制** | 执行中遇到计划外的情况：挂（等用户）、重规划（重新生成计划）、降级（跳过该步） |

### 3.3 什么时候用 Plan 而不是 ReAct

| 判断问题 | 答案"是"则倾向 |
|---------|---------------|
| 步骤是预先已知的吗？ | 已知 → Plan；未知 → ReAct |
| 任务链路长（>5 步）吗？ | 长 → Plan（ReAct 长链易发散） |
| 需要向用户展示进度清单吗？ | 需要 → Plan |
| 中途可能遇到大变化吗？ | 会 → ReAct（Plan 太死板） |

> **面试金句**：ReAct 和 Plan-and-Execute 的取舍本质是**"灵活度 vs 可预测性"**的权衡——探索型任务要灵活（ReAct），确定性长任务要可预测（Plan）。现代 Agent 框架（LangGraph）两种都内置，按任务类型切换。

## 4. Reflection：先做后审（质量守门员）

### 4.1 核心思想

**模型先生成答案，然后用另一个提示词（或同一模型的不同视角）审视自己的答案**，发现问题就重做，直到通过质检：

```
生成阶段：模型产出初始答案
  ↓
反思阶段 1（充分性）："资料查够了吗？" → 不够 → 重新检索再答
  ↓
反思阶段 2（幻觉检测）："每句话有出处吗？" → 没有 → 重新生成带引用
  ↓
反思阶段 3（有用性）："这答案对用户有用吗？" → 没用 → 重新组织
  ↓
通过 → 输出
```

### 4.2 两种实现方式

| 方式 | 说明 | 优缺点 |
|------|------|--------|
| **单一模型自反思** | 同一个模型生成→审查→重做 | 省成本，但模型可能"自己查自己查不出错" |
| **双模型互审**（Generator + Critic） | 一个生成，另一个专门挑错 | 挑错更狠，但多一次模型调用成本 |

### 4.3 Reflection 的真实价值场景

- **防幻觉**：答案要求带引用，无引用一律重做——这是 BondSeek 防幻觉体系的核心（自反思三重循环）
- **代码生成**：写码后"自己 review 再交"——能抓到大量低级错误
- **低错误容忍业务**：金融/医疗，答错代价高

## 5. 生产真相：三大范式是组合拳 ⭐⭐⭐

> **面试最加分的一句：真实 Agent 系统不会只用一种范式，而是嵌套组合。**

BondSeek 的实际组合就是一个活例子：

```
用户 → 编排层（Plan 的变体：Supervisor 决定派谁去）
         ↓
       专家 Agent 各自跑自己的循环（ReAct 骨架：想→工具→看）
         ↓
       每个答案过质检（Reflection：自反思三重循环）
         ↓
       不合格 → 重新生成（Reflection 的"重做"）
```

| 层级 | 范式 | 干什么 |
|------|------|--------|
| 编排层 | **Plan 思想**（Supervisor 委派） | 顶层决定"派谁、干几步" |
| 执行层 | **ReAct**（统一执行引擎） | 专家 Agent 边想边查 |
| 质量层 | **Reflection**（自反思三重循环） | 答案自查、不合格重做 |

**为什么必须组合**：
- 只用 ReAct → 质量不可控，答完没人审
- 只用 Plan → 太死板，探索型任务跑不动
- 只用 Reflection → 没有工具循环，反思完也没资料可查

> **面试金句**：范式不是单选题。生产上是**用 ReAct 的循环打底（灵活执行）、用 Plan 的思想约束顶层（编排委派）、用 Reflection 的质检收尾（质量把关）**——三者解决的是不同阶段的问题，组合起来才完整。

## 6. 面试回答框架（30 秒版）

### 送分版（只说定义）

> "认知架构有三大范式。**ReAct** 是边想边做——每步输出 Thought/Action/Observation 循环直到完成，适合探索型任务；**Plan-and-Execute** 是先计划后执行——模型先产出步骤清单再逐步执行，适合确定性长任务，可预测；**Reflection** 是先做后审——生成答案后自检，不合格重做，适合质量敏感场景。每个都是'思考与行动的组织方式'。"
> （够用，但只是"背书"）

### 加分版（说取舍 + 组合 + 结合项目）⭐

> "三大范式不是选择题。**ReAct** 灵活但容易发散、token 开销大；**Plan-and-Execute** 可预测但死板、计划跟不上变化；**Reflection** 提升质量但多付一轮思考成本。生产系统一定是组合拳——以我们 BondSeek 为例：顶层用 **Plan 思想**（Supervisor 决定派哪个专家 Agent）、执行层用 **ReAct 骨架**（统一执行引擎，换提示词和工具集变成不同角色）、质量层用 **Reflection**（自反思三重循环查充分性/幻觉/有用性，不合格把问题反馈给模型重生成）。三大范式对应解决编排、执行、质量三个阶段的问题。"
> （体现"我踩过坑、我做过系统"）

## 反模式（本主题避免）

- **把范式当单选题**——真实系统是嵌套组合，单一范式撑不起生产
- **ReAct 不设轮数上限**——模型可能无限循环调工具，必须 max_iterations + 熔断
- **Plan 计划的步骤是"大词"**——"分析债券"这种步骤无法执行，要拆成工具能完成的最小动作
- **Plan 没有重规划机制**——执行中遇到意外只会死撑或失败
- **Reflection 用同一模型同一提示词**——自检能力有限，关键场景用双模型互审
- **只反思不重做**——反思发现错了却不重新生成，等于白反思
