## ① 开门：加载历史（上下文）

**冲突：** Agent 是"无记忆的"——模型每次调用只看到你给它的那几段文字。用户说"继续上次的"，它得知道你上次说了什么；但对话历史会无限膨胀，而模型窗口有限。

**BondSeek 怎么解决：** 双轨存储（`context/` 模块）——
- **展示历史**（前端要看的）：永不压缩，原样存 PG
- **工作上下文**（模型要用的）：随时可压缩——两阶段渐进压缩（50% 剪枝 / 70% 摘要），枯树裁剪、旧内容折叠

**代价：** 双份存储增加复杂度和查询成本；压缩是"有损"的，细节可能被摘要吞掉。

> 📎 深挖：`session-compression-in-agent-systems.md` | `case-study-bondseek-memory.md`

---

## ② 记起你是谁：注入记忆

**冲突：** 即使用了压缩，模型仍然"不认识你"。它不知道你只买 AAA 级债券、喜欢简洁回答、最近关注利率债——这些是**跨会话的长期记忆**，每次都该带上，但带太多又污染窗口。

**BondSeek 怎么解决：** 三层记忆在对话开始时注入 system prompt：
- **L1 用户画像**（你是什么人）：结构化 tag 枚举，XML 全量注入——投资偏好 / 交互风格 / 领域聚焦
- **L2 情景记忆**（上次发生了什么）：对话级 facts.md / decisions.md
- **L3 知识记忆**（系统沉淀的领域知识）：全局 corrections.md / domain_knowledge.md

**代价：** 每次对话要额外调 LLM 召回记忆；画像注入有 token 成本（上限 2000）；记忆可能过时（用 stale 标记 + 月度清理兜底）。

> 📎 深挖：`case-study-bondseek-user-memory.md`（L1 专项）| `case-study-bondseek-memory.md`

**有个关键触发治理**：只有 `trigger=user`（真实用户对话）才走记忆链路，cron 定时任务和首页初始化一律跳过——**记忆是给"人"用的，不是给"机器"用的。**

## ③ 想清楚问的啥：Query 扩展

**冲突：** 用户的话是"模糊的短句"——"它涨价了没？"这种话拿去检索，什么都搜不到。**检索系统的痛点是"问都问不对，答怎么可能对"。**

**BondSeek 怎么解决：** Query 四步扩展（`retriever/query_processor.go`）：
1. **Rewrite 重写**：指代消解（"它"→"XX 债券"）+ 时间规范化（"最近"→"近 3 个月"）→ 单次 LLM 调用顺手抽关键词
2. **Step-Back 抽象**：退一步问宏观背景（"XX 债券近期走势"→"该行业整体行情"）
3. **Decompose 分解**：拆成 ≤5 个子问题
4. **Multi-Query 变体**：每个子问题并行生成 ≤3 种问法

**代价：** **代价极大**——每次检索前的预处理就 2+ 次 LLM 调用（Rewrite + 关键词 + Step-Back/Decompose/Multi-Query），延迟和成本肉眼可见。这是 BondSeek 选择"重管线"的明证：**费 LLM 但不费结果**。

> 📎 深挖：`case-study-bondseek-rag.md` §2

## ④ 决定派谁去：多 Agent 编排

**冲突：** 一个分析问题 = 技术面 + 基本面 + 可视化 + 研报组装。让一个 Agent 全干？上下文爆炸、职责混乱、一个环节崩全崩。让多个 Agent 各自为战？结果没人整合。

**BondSeek 怎么解决：** Supervisor 模式（`aistudio/` 模块）——
- **监工（Orchestrator）不干活**：只做理解意图、委派任务、整合结果
- **专家（SubAgent）被包装成工具**：`SubAgentTool` 把每个专家变成一个 function calling 工具，监工 LLM 自主决策"派谁、并行不并行、顺序如何"
- **每次调用全新子会话**：专家完全无状态，互不污染
- **只回摘要**：专家输出瘦身成"结论 + 文件路径"，不撑爆监工窗口
- **统一引擎**：所有角色共用同一 `ExecutionEngine`，只是"工具箱 + 岗位说明书 + 迭代上限"不同

**代价：** 多 Agent = 多轮 LLM 调用（成本翻倍）；LLM 决策"派谁"本身可能出错（用 system prompt 硬规则兜底）；编排链路深，故障点变多。

> 📎 深挖：`case-study-bondseek-multi-agent.md`

## ⑤ 去查资料：RAG 检索

**冲突：** 专家要回答"XX 债券信用风险如何"，但模型知识截止到训练时间，且容易**幻觉**（一本正经编造）。要"答得准"就得查资料；要"查得准"就得解决检索的技术难题——**语义匹配不准、多源数据打架、结果太旧、窗口放不下**。

**BondSeek 怎么解决：** 十步检索管线（`retriever/retriever.go`）——
- **三路并行召回**：chunk（文本）/ entity（实体）/ relation（关系）同时搜 Milvus
- **图谱搭桥**：实体命中的关系 → 反查证据 chunk（把图谱结果"翻译"回文本）
- **RRF 融合**：多路结果用倒数排名融合（只看名次不比分数）
- **Rerank 精排**：交叉编码器重排，取 Top30
- **时间治理**：partition 月份裁剪（防 OOM）+ exp 时间衰减（新闻/研报越新越相关）

**代价：** 检索管线又长又贵（Query 扩展 + 三路向量 + Rerank = 数次模型调用）；"重召回 + 精排"架构对基建要求高（要同时维护 Milvus + PG + 图谱）。

> 📎 深挖：`case-study-bondseek-rag.md`

## ⑥ 边做边说：SSE 流式

**冲突：** 模型生成见结果要几十秒，让用户干等？必须**边生成边推**。但流式会话必然遇到"推到一半断网"的问题。

**BondSeek 怎么解决：** SSE 流式输出 + 三层断线恢复（`agentcore/`）：
- **ReplayLogStore**：Redis Stream 持久化带 seq 的事件
- **CoreHydrator**：重连后"先补历史、再接实时"
- **水位线去重**：`seq <= watermark` 丢弃、缺口缓冲、日志补发

**代价：** 每次事件都要写一次 Redis（性能开销）；日志有 TTL 上限（2h/2000 条），超时没重连就追不回来了。

> 📎 深挖：`case-study-bondseek-sse-recovery.md`

## ⑦ 防失败：降级与重试

**冲突：** LLM 会超时、工具会报错、专家会崩。如果崩一次整个对话就完蛋，用户体验就是"AI 真脆"。

**BondSeek 怎么解决**（`core/engine.go` + 各案例共通）：
- **LLM 指数退避重试**：3 次重试，延迟 200/400/600ms；已向客户端发过内容则不重试
- **工具 3 连败硬降级**：同一工具连续失败 3 次 → 硬拦截 + 注入"停止重试，说明不可用后完成"
- **宽容完成**：达到迭代上限但已有产出文件 → 算成功
- **增强路径永不拖垮主链路**：RAG 失败回退原查询、子 Agent 失败监工接着整合、图谱遍历失败用 Fast 结果

**代价：** 大量优雅降级代码（每处都是 `if err != nil { fallback }`）；"宽容完成"可能掩盖真相（产出文件 ≠ 结果正确）。

---

## ⑧ 断线不怕：seq 回放（见 ⑥）

*此处与 ⑥ 同一机制，不重复。核心记住：**断线恢复 = 用"我收到第几号了"这个整数，从日志往后补。***

---

## ⑨ 整合交付：监工总结

**冲突：** 专家产出了 CSV、图表、分析 MD——但用户要的是一句"XX 比 YY 更值得买，因为……"。**零散成果必须被整合成可读结论。**

**BondSeek 怎么解决：** 监工收齐所有专家的"摘要 + 文件路径"后，自己调 LLM 整合输出（System Prompt 约束：≤1000 字、克制 emoji、不复述专家产出——"专家详细产出已在文件里，不要复述"）。

**代价：** 监工的整合质量依赖 LLM；如果专家产出不全，监工可能在信息不足下整合（靠 system prompt 规定失败时"列出已产出，不声称完成"兜底）。

---

## ⑩ 记住这次：记忆异步写入

**冲突：** 对话结束了，但这轮发现了"用户喜欢简洁""用户关注城投债"——**不记下来，下次又得重新猜**。可如果在回复前同步写记忆，又拖慢用户体验。

**BondSeek 怎么解决：** **异步 + 异步的钱兜底**——
1. 对话结束 → `go goroutine` 异步发布 ingest 事件到 NATS（30s 超时，不阻塞回复）
2. `SleeptimeWorker` 实时消费，走四道质量闸 + 价值评分（≥0.85 置信 / 有证据 / 过黑名单 / 评分≥8）
3. **失败不重试会丢** → `Scheduler` 每 10 分钟扫描未抽取分段补偿重投（≤5 次）
4. 写入是全链路"整批放弃"——评分失败就不 commit 不标记，等补偿，**绝不放行污染记忆**

**代价：** 异步链路复杂（NATS + Worker + Scheduler 三件套）；记忆写入有延迟（最坏 10 分钟补上）；异步失败路径多，审计成本高。

> 📎 深挖：`case-study-bondseek-user-memory.md` §3、§8

## 💎 核心章节：Agent 系统的 5 大设计哲学（读完全库只带走这 5 句）

> 这是从全部案例里**萃取出来**的、可迁移到任何 Agent 系统的心智模型。面试答任何 Agent 题，用这 5 句话当"底层逻辑"都成立。

### 🥇 哲学一：LLM 不可信 → 确定性规则兜底

**现象：** BondSeek 处处不信 LLM——画像写入有四道闸、dedup 有 explicit/inferred 博弈表、RAG 有三次 LLM 调用后还有确定性过滤、工具失败有硬降级。

**公式：** `LLM 负责"高智商处"（理解/决策/生成），确定性代码负责"高确定性处"（校验/过滤/兜底）——让模型发挥创造力的地方，一定在规则能兜住的范围里。`

**面试用法：** 被问"如何防止 Agent 出错" → 答"不是防 LLM，是设计'LLM 在前、规则在后'的管线，规则兜底让错误不可达"。

### 🥈 哲学二：上下文是稀缺资源 → 治理优先级最高

**现象：** 双轨存储（展示不压、工作压）、子 Agent 只回摘要、RAG Top30 截断、动态提示词保 static + 刷 dynamic、图像注入限 2000 token——**BondSeek 的每个模块都在守卫上下文窗口**。

**公式：** `上下文是 Agent 唯一的"内存"，一切设计优先回答：什么进窗口、什么不进、进了怎么退。`

**面试用法：** 被问"为什么 Agent 要管理上下文"→ 答"窗口是硬约束，上下文治理决定 Agent 能处理多复杂的问题"。

### 🥉 哲学三：分离与隔离是协作的前提

**现象：** 会话隔离（子 Agent 全新子会话）+ 工作区共享（成果可跨专家读）；状态在 DB 不在内存；记忆按 L1/L2/L3 分层；技能按 scope 分权限。

**公式：** `该隔离的隔离（状态、上下文、权限），该共享的共享（成果、数据）——隔离防污染，共享促协作。`

**面试用法：** 被问"多个 Agent 怎么协作不打架"→ 答"上下文会话隔离 + 文件工作区共享，两维度同时管理"。

### 🏅 哲学四：一切数字化 → 收敛成"可比较的量"

**现象：** 断线恢复把"丢重乱"收敛成 seq 整数比较；画像把"用户偏好"收敛成 tag 枚举 + confidence 数值；RAG 把"多路结果"收敛成 RRF 分数；陈旧收敛成"90 天"。

**公式：** `模糊的问题先找"一个可比较的数字/枚举"——有了它，判重、排序、阈值、衰减全部变成机械操作，可审计可预测。`

**面试用法：** 被问"如何评估记忆/结果"→ 答"先把质量转成数值（置信度/分数/序号），再用阈值和排序做决策"。

### 🎗️ 哲学五：增强永远不拖垮主链路（优雅降级是默认能力）

**现象：** Query 扩展失败用原查询、Rerank 失败用 RRF 顺序、图谱遍历失败用 Fast 结果、记忆不阻塞回复、子 Agent 崩溃不影响监工整合。

**公式：** `每个"锦上添花"的环节都必须回答一个问题：它挂了，主链路还走不走？答案永远是"走"。`

**面试用法：** 被问"Agent 服务稳定性"→ 答"区分必要链路和增强链路，增强全部可降级，失败只记日志不阻断"。
