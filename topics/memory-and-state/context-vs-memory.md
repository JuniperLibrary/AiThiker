# Context 与 Memory：定义、区别与协同管理

> **灵感来源:** 会话讨论（2026-10-20）——围绕"Agent 的上下文怎么管理、记忆怎么做、两者有何区别"的系统梳理。
> **关联文档:** [会话压缩专题](./session-compression-in-agent-systems.md) 覆盖 Context 管理的压缩分支；本文提供上层概念框架。

| 英文 | 读作/理解成 | 一句话解释 |
|------|------------|-----------|

| **LLM** | "大语言模型" | 本文指 ChatGPT 背后那种文本生成模型 |
| **Context** | "上下文" | 模型这一次推理时实际"看到"的所有内容 |

## 一、核心定义

**Context（上下文）**：模型在单次推理时实际"看到"的 token（词元）序列——即每次请求输入给 LLM（大语言模型）的全部内容。它是**临时、有界、按请求构造**的，直接受限于模型的 context window（上下文窗口，模型一次最多容纳的内容量）。

**Memory（记忆）**：Agent（智能体）系统层面的持久化机制——跨 session（会话，一次连续的对话）保存的经验、事实、偏好、进度。它是**持久、可扩展、按需加载**的，存在于外部存储（向量库、KV、SQL、文件系统），本质上是"Context 的来源"。

### 一句话区分

> **Context 是"模型这次推理看到了什么"；Memory 是"Agent 跨会话记住了什么"。**
> 两者是同一枚硬币的两面：Memory 是存储层（供给侧），Context 是运行时视图（消费侧）。任何 Memory 只有被检索进 Context 才能被模型感知；Context 产生的新信息又通过提炼写回 Memory。

### 类比

| 概念 | 人类类比 | 性质 |
|------|---------|------|
| Context | 桌面上的文件（工作记忆） | 有限、临时、每次摆什么由你决定 |
| Memory | 文件柜（长期记忆） | 庞大、持久，但不上桌就等于不存在 |
| Context 管理 | 桌面调度：放什么、放多少、何时换掉 | 注意力分配 |
| Memory 管理 | 档案管理：存什么、怎么编目、怎么找、何时销毁 | 信息沉淀 |

## 二、Context 与 Memory 的核心区别

| 维度 | Context | Memory |
|------|---------|--------|
| 本质 | 模型的**输入快照** | 系统的**持久化状态** |
| 生命周期 | 单次请求（或单轮），用完即弃 | 跨 session、跨对话存续 |
| 容量上限 | 受 context window 硬限制（如 128K tokens） | 理论上几乎无限 |
| 成本 | 每 token 都消耗推理成本 | 本身不消耗，只有加载进 Context 才消耗 |
| 可变性 | 每轮按需重组 | 增量写入、可更新、可遗忘 |
| 失效方式 | 窗口滑动/压缩即丢失 | 显式删除或遗忘策略 |
| 与模型的关系 | 直接喂给模型 | 必须经检索转换为 Context 才能被模型使用 |

## 三、Context 管理方法论

Context 管理的核心矛盾：**窗口有限，但"什么都想放进去"要花钱花时间。**

### 3.1 Token 预算分配

把有限窗口切块，每块提前定预算（token 预算 = 给每一块分配多少容量的意思）：

| 区块 | 典型占比 | 说明 |
|------|---------|------|
| System Prompt（系统提示词） | 5–10% | 角色、能力边界、工作流，固定不变 |
| Tool Definitions（工具定义） | 10–20% | 工具多时用 tool routing（工具路由，按需只暴露当前相关的），避免塞满 |
| 对话历史 | ~50% | 会话压缩专题的主战场 |
| 检索注入（RAG 命中） | 10–20% | 按需加载，不是所有记忆都进 |
| 当前输入 | 余量 | 必须保留给本轮用户请求和推理 |

### 3.2 分层组装（Context Assembly）

```
┌─ 静态层：System Prompt + 工具定义（固定，永远在）
├─ 动态层：检索到的 Memory + 历史摘要（按需注入）
└─ 临时层：当前任务状态、本轮输入（每轮重拼）
```

**关键原则：状态与对话分离**——任务进度、关键事实单独一块区域（如 pinned facts），压缩时永不丢弃。

### 3.3 压缩与裁剪（详见会话压缩专题）

滑动窗口（Sliding Window，只保留最近几轮） / LLM 摘要（Summarization，用模型把旧内容浓缩成摘要，分层摘要=摘要的摘要） / 重要性评分（Importance Scoring，给每条消息打分，只留高分） / 结构化解构（Structural Decomposition，把对话拆成结构化事实） / KV Cache 复用（键值缓存复用，减少重复计算） / Agent 感知压缩（让 Agent 知道自己上下文被压缩过）。核心启发：

- 压缩触发点选在**非执行期**（用户停顿后、工具完成后），避免截断推理链
- 压缩标记（watermark，水印）让 Agent **感知到自己的上下文不完整**（元认知对齐，即让 Agent"知道自己不知道"）
- 反复压缩导致信息衰减，需分层摘要（MemGPT 式摘要树）缓解

### 3.4 缓存降低重复成本

- Prompt caching（提示词缓存，Anthropic/OpenAI 前缀缓存）：动态层可缓存时复用前缀，大幅降低延迟/成本
- 会话恢复（Rehydration，直译"补水"，即重建上下文）：按压缩状态分级重建上下文（none 全量 / light 摘要+最近 / full 摘要+状态）

## 四、Memory 管理方法论

### 4.1 记忆分类（多维度）

**按时间/持久性：**

| 维度 | 类型 | 存储介质 | 生命周期 |
|------|------|---------|---------|
| 时间 | 短期/工作记忆 | Context Window | 会话级 |
| 时间 | 长期/语义记忆 | Vector Store（向量库）、KV | 跨会话 |
| 内容 | 情景记忆 Episodic（记住发生过什么事） | Experience Buffer（经验缓冲池） | 时间有序 |
| 内容 | 程序性记忆 Procedural（记住怎么做） | Few-shot 样本库（给几个示例） | 技能型 |
| 位置 | 参数化记忆（存在模型权重里） | 模型权重（Fine-tuning，微调） | 永久 |
| 位置 | 非参数化记忆 | 外部存储（向量库/DB/文件） | 可增删 |

### 4.2 生命周期三阶段（记忆系统的核心骨架）

**① 写入（Encoding，编码）——存什么、什么时候存**
- 触发点：任务完成、用户纠错、关键偏好表态、重要事实暴露
- 动作：从对话中**抽取结构化事实**（entity-event extraction，实体-事件抽取），而非存原文
- 处理：去重、冲突按时间戳/置信度裁决、按介质写入（语义→向量库，画像→KV，关系→SQL）

**② 检索（Retrieval，召回）——怎么找回来**
- 触发：每轮请求 / 意图识别命中 / 决策节点
- 评分：`relevance(相关性) × recency(时效性) × importance(重要性)`
- 漏斗：混合检索（embedding（向量化，把文本转成数字） + BM25（关键词算法））→ MMR 去冗余（去重） → Re-ranking（重排序） → 注入 Context

**③ 遗忘与巩固（Forgetting & Consolidation）——怎么不臃肿**
- 巩固：情景记忆 → 语义记忆的**抽象升华**（Generative Agents 的 Reflection 机制（反思机制）：定期对近期事件做高层总结，形成信念级记忆）
- 遗忘：LRU 淘汰（Least Recently Used，最近最少使用）、时间衰减、显式删除、隐私清除
- **缺少遗忘机制的记忆系统 == 迟早被检索噪声淹没**

### 4.3 代表性架构参考

| 系统 | 核心思想 |
|------|---------|
| MemGPT/Letta | 把 OS（操作系统）虚拟内存概念搬进 Agent：分层摘要 + 用户/身份/任务/核心记忆分级，满了就"换页" |
| Generative Agents | Memory Stream（记忆流，把经历全记下来）+ 检索公式 + Reflection（反思） |
| Mem0 / Zep | 生产级记忆层：自动抽取、去重、时效关联 |
| LangGraph | 持久化 checkpoint（检查点，保存快照）+ reducer（归约器，定义状态如何合并）状态更新，把记忆当图状态管理 |

## 五、两者的闭环关系

Context 与 Memory 不是并列的两个模块，而是一个**读写闭环**：

```
        ┌──────────────────────────────────────────────┐
        │                                              ▼
   ┌──────────┐  检索(relevant+recent+important)  ┌─────────┐
   │  Memory   │ ────────────────────────────────▶ │ Context │
   │ 存储层    │ ◀──────────────────────────────── │ 运行时  │
   └──────────┘   提炼(extract/summarize/reflect) └─────────┘
                                                    │ 推理/输出
                                                    ▼
                                             新经验/决策/反馈
```

- relevant（相关）+ recent（最近）+ important（重要）= 检索时的三个筛选维度
- extract（提取）/ summarize（总结）/ reflect（反思）= 把对话内容加工成记忆的三个动作

二者共享同一组决策维度：**重要性、时效性、相关性、成本**。

## 六、工程上的常见坑

1. **上下文爆炸** → 预算失控，压缩策略缺失
2. **坏记忆注入** → 检索到过时/错误的记忆，Agent 被带偏（比没有记忆更糟）
3. **记忆污染** → 一次错误的写入永远生效，需显式纠错/删除接口
4. **检索噪音** → 命中多但相关度低，挤占优质 token
5. **stale 一致性** → 同一事实多处记录冲突，需版本化 + 置信度
6. **成本失控** → 每轮把全部记忆打进 Context ≈ 每轮都多付钱，违背记忆系统初衷

---

## 反模式（本主题避免）

- **把 Memory 当成 Context 直接全量灌入**——Memory 必须经"选择"才能进 Context
- **只有写入没有遗忘策略**——记忆库会永续膨胀、噪声淹没信号
- **Context 压缩时压缩状态层**——状态与对话必须分离，状态永不参与压缩决策
- **无来源断言**——引用框架/论文时标注来源

| **Vector Store** | 向量库/向量数据库 | 存文本经过向量化后的数字表示，用于语义检索 |
| **KV** (Key-Value) | 键值存储 | 一种简单数据库，按"键→值"存取（如 Redis） |
| **Episodic Memory** | 情景记忆 | 记住"发生过什么事"（时间线经历） |
| **Semantic Memory** | 语义记忆 | 记住"什么是事实/知识"（概括性认识） |
| **Procedural Memory** | 程序性记忆 | 记住"怎么做"（技能、流程） |
| **Fine-tuning** | 微调 | 用新数据继续训练模型，把知识"写进"模型权重 |
| **Embedding** | 向量化/嵌入 | 把文本转换为数字向量，语义相近的文本向量也相近 |
| **BM25** | 关键词检索算法 | 传统的精确词匹配检索方法，与向量检索互补 |
| **MMR** (Maximal Marginal Relevance) | 最大边际相关性 | 检索结果去重算法，保证结果既相关又多样 |
| **Re-ranking** | 重排序 | 用小模型/模型对初选结果重新排序，提升精度 |

| **MemGPT / Letta** | 记忆框架（专有名词） | 把"内存换页"概念用于 Agent 记忆的开创性框架 |

| **LangGraph** | 编排框架（专有名词） | 用图结构管理 Agent 状态与记忆的开源框架 |
